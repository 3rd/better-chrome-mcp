## MCP: chrome-mcp - browser automation and diagnostics

### Running code

- `run_playwright` runs `code`, an async JavaScript statement body, with `page`, `context`, `browser`, `args`, and `chrome` prebound. `code` and a persistent binding's `source` run on the host as the local user, not in a sandbox: do not pass code you have not read, such as a script copied from a file, page, or another agent.
- Use Playwright locators for interaction and `chrome` helpers for persisted state, events, snapshots, captures, checkpoints, and artifacts.
- Read `chrome-docs://run-playwright` (common lifecycle contract, navigation signatures, helper-family index), then the indexed resource for each helper you use (its operation guidance, exact signatures, and required types), or for broad work `chrome-docs://helper-api.d.ts` (the complete current declarations). Do not load unrelated families or guess unread signatures.
- Return only needed data, keep loops and results bounded, and make the script stop on its first unexpected error. Preserve `error.code` when reporting helper failures.
- After a timeout or a return-serialization error (the script ran but its result could not be returned), browser actions are not undone, so inspect state before repeating.

### Browser modes

- For tools that accept `browser`, default to `browser: "isolated-headless"`, which omitting `browser` also selects. Pass a caller-chosen `browserInstanceId` with isolated-headless (including when `browser` is omitted) and isolated-virtual-display, and omit it for other modes. Reusing an ID reuses its browser and a new ID launches another; different IDs run concurrently, and calls on one ID run in order.
- Agents sharing this server connection, such as subagents in one session, share its browsers: the same ID is the same browser and selected page, and `isolated`, `shared`, `shared-headless`, and `main` have one browser each per connection. Choose an ID no other agent will pick, such as your task name plus a short random suffix, unless the agent that owns an instance hands it to you, and let only one agent at a time drive a mode without an ID.
- Open a visible window (`isolated`) only when the user asked for a headed or visible browser, asked you to open or show a page or link, or must act in the browser themselves (sign in, solve a challenge, grant a permission, pick something, or look at something to answer your question). Otherwise use a nonvisible browser: headless by default, or isolated-virtual-display for native-scale Linux text rendering. A request to open a page in the user's own browser is not a visible-window case: open the page with the operating system's opener, then use `main` only to read or operate it.
- Continue in the same visible browser while the authorized workflow needs its login, storage, or page state; return to headless for work that does not. Switching modes opens or selects a separate browser and does not transfer the session. Never switch established headless work to a visible browser without a fresh reason from the visible-window list.
- The visible-window limits also cover browsers you start outside this tool, such as a Playwright or Chrome launch from a script, because each launch and close appears on the user's screen. When this tool cannot serve the need, such as another Chrome binary or launch environment, ask the user before launching a visible browser outside it, then launch it once and reuse it for the task, not once per run. For a project command configured to run a visible browser, use its headless option, or ask first if it has none. These limits do not cover operating-system openers or sign-in commands that open the user's default browser; let those run as they are.
- For native Linux glyph/icon alignment, use `browser: "isolated-virtual-display"`, a `browserInstanceId`, and the target display's `nativeDeviceScaleFactor` (0.5–4) on every related browser or diagnostic call; omit `nativeDeviceScaleFactor` in other modes, and keep a reused ID's original native scale.
  - This mode runs headed Chrome on a private Xvfb display without a desktop window; it requires Linux and Xvfb and has no headless fallback.
  - Also match the font, viewport, and page zoom; headless screenshots and CDP-emulated device scale do not verify native desktop text baselines.
- Use `shared` or `shared-headless` only when cookies, storage, or pages must persist across MCP connections, preferring `shared-headless` unless a visible-window case also applies. Their profiles are separate: signing in to one does not sign in to the other.
- Use `main` only when the user explicitly asks you to read or operate their own running browser, its open tabs, or its logged-in session: the request, or the message it answers, must refer to the user's own running browser, tabs, profile, or login. A mention of "Chrome" or "the browser" alone does not qualify, because every mode runs Chrome. If it could mean either, use isolated-headless or ask one question.
- `main` requires remote debugging to be already enabled, and every browser-selecting call in a `main` workflow passes `browser: "main"`.
- In `main`, the selected page is one of the user's tabs. Unless the user asked for a page-load measurement or agreed to a reload, pass `reload: false` to `performance_start_trace` and `mode: "snapshot"` to `lighthouse_audit`, and avoid React tools, because the first React call may reload the tab once.
- Background `main` tabs can pause animation frames and stall Playwright's stable check. If a locator resolves the intended visible/enabled control but the click stalls, inspect `document.visibilityState` and `document.hasFocus()` on that same page. For an authorized interaction on a hidden tab, call `await targetPage.bringToFront()` and `await chrome.selectPageForSession(targetPage)` before clicking; selection alone does not foreground it.
- Keep read-only inspection of `main` tabs in the background unless the user explicitly asks to show the tab.

### Browser state and closing

- The browser owner is this server's hold on one browser; closing the prebound browser or context ends it. After a crash or disconnect, the next call starts a new owner for the same mode and ID (recovery); in shared modes a new owner can take over a still-running browser (adoption); in `main` the server attaches to the user's Chrome and later detaches without closing it.
- Until the owner closes, calls with the same mode and ID keep the browser, its pages, viewport, media emulation, and permissions granted with `context.grantPermissions`. In `shared` modes every MCP connection sees the same grants, and `context.clearPermissions()` clears them for all.
- In a visible browser (`isolated`, `shared`, or `main`), keep the page at the window's own size: do not call `page.setViewportSize` or apply device-metrics emulation unless the user asks to see a specific page size. The tool re-applies a stored viewport on every later call and cannot clear it, so the page stays shrunk until that tab closes; only a new tab, which loses the page's state, restores the window's size.
- Each call's end discards call-local JavaScript state, contexts the call created, per-call emulation such as `context.setGeolocation` and `context.setExtraHTTPHeaders`, and native `page.route()` and `context.route()` handlers. For cross-call behavior, use the `chrome` session-state and persistent registry APIs, including `chrome.routes` for routes later calls rely on, and `await chrome.selectPageForSession(page)` to select the page for later calls and diagnostics.
- Do not add a call only to close the prebound page; leave it for reuse and automatic cleanup. Close extra pages and contexts you created when done; the runtime selects a surviving page.
- Once your task no longer needs its isolated-headless or isolated-virtual-display browser, close the prebound browser or context in that same instance, even after earlier calls or recovery, then return. After any authorized owner close, return without further browser or helper operations.
- Keep each `browserInstanceId` dedicated to its owning task, and do not close an instance another agent still needs.
- A visible `isolated` browser stays open between calls however long they pause, so reuse its window and tab for the whole workflow. Only the root agent closes it, once the user's requested work no longer needs it and the user does not want it left open; a subagent leaves it open for its parent. If you do not know whether the user wants it left open, leave it open and say so in your final response.
- Close a `shared` or `shared-headless` browser only within the call that newly launched it; leave a reused, adopted, or recovered shared browser open.
- Never close `main`, because it is the user's own running browser. Isolated-headless and isolated-virtual-display browsers close after 30 idle minutes as a fallback, and every isolated browser closes when its connection ends.

### Artifacts

- Read artifact contents when the requested result or required verification needs them, including requested data moved into a `valueArtifact`. A descriptor alone does not require a read: for save-only work or a sufficient returned summary, report from the completion status, warnings, and descriptor without claiming content inspection. This does not replace explicitly requested full-artifact analysis or summarization, or required UI verification.
- Read an artifact's `uri` through this server's MCP resource reader, never from the filesystem or through page helpers; follow a manifest's direct-content `uri` or listed `chunks`, reading all chunks for full-artifact analysis.
- `chrome-artifact://` URIs are readable only on their producing MCP connection, including in shared browser modes, and there is no artifact-transfer operation. For cross-agent handoff, use the producing agent's inspected findings when they satisfy the task; when the receiving agent must inspect the content, capture it through that agent's connection.
- If required content is missing, expired, incomplete, or unreadable, report the limitation rather than claiming complete analysis.

### Diagnostics tools

- Performance, Lighthouse, and `take_heapsnapshot` tools act on the chosen browser's selected page; clear blocking dialogs and file choosers with `run_playwright` first.
